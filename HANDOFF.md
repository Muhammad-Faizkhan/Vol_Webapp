When building/fixing any screen, verify no horizontal scroll with a Playwright script that checks `document.documentElement.scrollWidth` vs `clientWidth` at 320/375/768/1024/1440/1920 — don't rely on eyeballing screenshots (a flex child missing `min-w-0` silently overflows even when it looks fine in a screenshot at one width, as happened with the portfolio-URL input on `/create-profile`).

**Recurring bug patterns found and their fixes** (useful if more screens are added later):
1. **Card grids used `flex gap-N` with fixed-px-width cards** (`WorkspaceCard`, `ClassCard`, `ProductCard` all had hardcoded `w-[300px]`/`w-[460px]`). Fixed by making the cards themselves `w-full` and switching every container to `grid grid-cols-[repeat(auto-fit,minmax(Npx,1fr))] gap-N` — this reflows correctly at any width, unlike `flex-wrap` with `flex-1` children (which HANDOFF's component-library section already warned doesn't wrap, it just squishes everything onto one line).
2. **Two/three-column dashboard layouts with a fixed-px side panel** (members/activity panels, folders sidebar, role-definitions panel, trending-canvases panel) used `lg:flex-row`. At exactly 1024px the persistent 400px app sidebar leaves only ~524px of content width, which a 280–400px fixed panel plus any real content can't fit in — bumped these specific splits to `xl:flex-row` (2-panel) or `2xl:flex-row` (the 3-panel Files tab), and added `min-w-0` to the non-fixed sibling column. Without that `min-w-0`, the fixed-width sibling (with `shrink-0`) still gets pushed past the viewport edge because the flexible column's own content sets an "automatic minimum width" that flexbox won't shrink below — this is the single most common cause of overflow found in this pass, worth checking first on any future flex-row split.
3. **Plain `<input>`/`<textarea>`/`<select>` elements with no `w-full` class** render at the browser's tiny intrinsic default width instead of filling their container (found in the create-post modal and the add-product form) — easy to miss since it's a visual/functional bug, not an overflow one.
4. **`Modal` component (`src/components/ui/Modal.tsx`) set a literal pixel `width` via inline style** (e.g. 1420px for the select-canvas modal) — always wider than a phone screen. Changed to `max-width` + `w-full` + outer padding so it fills up to the cap and shrinks below it.
5. **The canvas editor screens** (`(canvas)/canvas/[canvasId]`, `(canvas)/discover-canvas/[postId]`) are genuine CAD-style drawing surfaces with literal scaled-pixel content (e.g. `left-[170px] w-[591px]` representing a to-scale floor plan) — deliberately left non-reflowing, same as Figma/Miro's own canvas; only their header toolbars (which aren't part of the canvas surface) were fixed to wrap/scroll instead of forcing page overflow.

Data tables with fixed-px columns (home's recent-canvases table, the workspace members table) were wrapped in a contained `overflow-x-auto` + `min-w-[640px]` inner div rather than redesigned into cards — the table scrolls horizontally within its own box, the page itself never does.

## Follow-up: AuthShell had a boxed-in internal scrollbar at normal laptop heights

After the responsive pass above, the user reported (with a screenshot) that at 100% browser zoom the auth screens showed a cramped internal scrollbar — the content pane had its own tiny scroll box instead of the page just scrolling normally. Any auth screen whose content is taller than `viewport height − 120px` — which is most of them on a real laptop screen (e.g. 1920×868 with browser chrome) — got trapped in that inner scrollbox instead of the page scrolling. Verified via Playwright across 320–1920px width × 700–1080px height with no leftover boxed scroll or horizontal overflow. If a future session touches `AuthShell` again, don't reintroduce a `max-h` + `overflow-y-auto` on the content column — let the page scroll.

### Theme system (now built)

- `src/components/theme/ThemeProvider.tsx` — React context (`useTheme()` → `{theme, setTheme, toggleTheme}`), persists to `localStorage` key `vol-theme`, applies `data-theme="light"|"dark"` on `<html>`. Exports `THEME_INIT_SCRIPT`, a blocking inline `<script>` injected in `src/app/layout.tsx`'s `<head>` that sets the attribute before first paint (prevents flash-of-wrong-theme). Default theme is `"light"` for new visitors.
- `src/app/globals.css` has `@custom-variant dark (&:where([data-theme="dark"], [data-theme="dark"] *));` right after the `@import "tailwindcss";` line — this is what makes Tailwind's `dark:` variant key off the toggle instead of OS `prefers-color-scheme`. Don't remove this or `dark:` classes silently stop working.
- New CSS tokens in `globals.css` (both the raw `--var` under `:root` and the `--color-*` mapping under `@theme inline` — **always add both halves** or the Tailwind class won't generate): the existing `--dak-*` tokens (`dak-bg #050505`, `dak-heading #f4f4f6`, `dak-body #c8cbd0`, `dak-cta #9436fb`, `dak-muted #777a82`, `dak-line #c793ff`, `dak-surface #121212`, `dak-border #2b2b31`) are used for **dark theme** everywhere (not just auth screens anymore). New `--app-*` tokens for the **light dashboard theme**: `app-bg #fbf8ff` (page background), `app-sidebar-active #4a1b7d` (darker-purple active-nav pill in light mode — note dark mode's active pill uses `dak-cta` instead, the bright purple, since the dark sidebar itself is near-black not purple), `app-badge #d0a6fc`, `app-dark-surface #020204` (the near-black "Create Canvas"-style button / table-header color, used identically in both themes).
- **Established pattern, demonstrated in `Sidebar.tsx`, `AppHeader.tsx`, `(app)/layout.tsx`, and `(app)/home/page.tsx`** (treat these four files as the reference implementation for every other screen): the existing light-theme Tailwind classes (`text-auth-navy`, `border-light-border`, `bg-[#f8f9ff]`, etc.) were already verified correct against Figma's real Home screen in an earlier pass (14/16 exact hex matches), so **don't recolor the light classes** — just add a `dark:` variant next to each one using the `dak-*` tokens. **Bugs found across multiple agents' work and fixed by the coordinator afterward — worth knowing about if this pattern recurs**:

1. **Bright purple thumbnail bug**: `bg-auth-navy dark:bg-dak-cta` is the correct pattern for a *small* icon accent badge (e.g. a 40px square icon chip), but three different agents also applied it to *large* image-placeholder blocks (workspace/class/product card thumbnails, ~130-210px tall) — turning what should be a neutral "no image yet" placeholder into a solid, jarring bright-purple block. Fixed by changing those specific large placeholders to `dark:bg-dak-surface` (neutral dark grey `#121212`) across `WorkspaceCard.tsx`, `ClassCard.tsx`, `ProductCard.tsx`, `ProfileOverview.tsx`, `(app)/profile/page.tsx`, `(app)/explore/page.tsx`, and `(canvas)/canvas/[canvasId]/page.tsx`. **Rule of thumb for any future screen**: `dark:bg-dak-cta` (bright purple) is for small interactive/accent elements only (icon chips, active states, CTAs) — large placeholder/content-image backgrounds should use `dark:bg-dak-surface` or `dark:bg-dak-bg` instead.
2. **Real root cause of the theme-persistence bug** multiple agents independently ran into (and which the auth-flow-only pass earlier in this doc had already worked around, incompletely): `AppHeader`'s sun/moon toggle icon branched on `theme === "dark"` in JSX. Since SSR has no access to `localStorage`, the server always renders the "light" branch, while the client's first paint may show "dark" (from the blocking init script) — a genuine server/client markup mismatch. React's hydration-mismatch recovery then discards and rebuilds a big chunk of the tree client-side, which is what was silently reverting the `<html data-theme>` attribute a few hundred ms after every fresh page load (not just on reload — on *every* fresh navigation to a page with `dark:` classes, defeating the whole feature intermittently) and throwing a genuine `Uncaught Error: Hydration failed` in the console. **Fixed properly** (not just worked around) in `src/components/layout/AppHeader.tsx`: both the sun and moon SVGs now always render in the DOM; which one is visible is controlled by CSS (`hidden dark:block` / `block dark:hidden`), never by a JS/React branch on `theme`. This eliminates the hydration mismatch at its source. The earlier `useEffect` in `ThemeProvider.tsx` that re-asserts `data-theme` on mount/theme-change is still in place as defense-in-depth (harmless, and it's the textbook-correct way to sync React state to an external DOM attribute) but the AppHeader fix is what actually stopped the mismatch from happening in the first place. **If a future screen adds any UI that branches its rendered DOM structure (not just Tailwind classes) on `useTheme()`'s `theme` value, it will reintroduce this exact bug** — always prefer `dark:` CSS classes over `theme === "dark" ? A : B` JSX branches for anything that renders during initial mount.
3. `layout.tsx`'s `<body>` didn't have a `dark:bg-dak-bg` class, so on a very short/fast paint the body could show its default white background before the child content's own themed background covered it. Fixed by adding `dark:bg-dak-bg` directly to `<body>`.

## Follow-up: viewport-fluid layout pass (screens were built at literal Figma 1920×1080 dimensions)

The user pointed out that these screens used heights/spacing copied directly from the Figma canvas, which caused vertical scrolling on real browser viewports (browser chrome — tabs, address bar, bookmarks — reduces `window.innerHeight` below 1080 even at 100% zoom and even on a 1920-tall display, and further below that on a smaller laptop screen like 1366×768). This is a **different** axis of responsiveness than the earlier "no horizontal scroll at any width" pass — this one is about vertical fit at realistic desktop heights.

**Approach**: `min-h-screen` → `min-h-[100dvh]` (kept as `min-height`, not fixed `height`, so a page that still doesn't fit after compression falls back to a normal page scroll rather than an internal boxed scrollbar — the boxed-scrollbar pattern was already rejected earlier in this doc). Fixed-size illustration images switched to `h-[clamp(min,Ndvh,max)] w-auto` with `object-contain` so they shrink proportionally on short viewports instead of forcing extra page height. Every significant fixed `gap-N`/`py-N`/`size-N` value on the 9 auth/onboarding screens (`AuthShell`, Login, Sign Up, Forgot/Reset Password, OTP Verification, `join-network`, `join-network-dark`, Create Profile, Network Visibility) and their shared components (`RoleCard`, `OtpInput`) was converted to `clamp(minPx, Ndvh, maxPx)` so spacing compresses smoothly as available height shrinks, rather than staying rigid. Tuning was done empirically with a Playwright script measuring `document.documentElement.scrollHeight` vs `clientHeight` at two simulated "real browser" sizes — `1366×668` and `1920×980` (980/668 ≈ 1080/768 minus ~100px of chrome) — iterating the clamp minimums down until each screen fit, rather than calculating spacing by hand.

**Result**: at 1920×980 (a realistic full-size desktop browser window), 8 of the 9 screens now fit with **zero scroll** (`login` is off by 5px, imperceptible); `create-profile` — the longest form (photo upload + 5 more fields + submit) — is off by 19px, also effectively negligible. At the much shorter 1366×668 (a small laptop screen), most screens fit exactly or within ~40px; `create-profile` still has ~169px of residual scroll there because it's a genuinely long form and there's a practical floor below which shrinking touch targets/text further would hurt usability more than the residual scroll does — this was a deliberate trade-off, not an oversight. **The rest of the app (dashboard/workspaces/classrooms/discover/business/profile/canvas-editor) has not had this same fixed-height audit done** — those pages use `min-h-screen`/normal flow already (not literal fixed 1080px heights copied from Figma) so they're less likely to have the same problem, but they haven't been specifically verified against the two target viewport sizes the way the auth/onboarding screens now have been.

## Known environment issues (discovered this session — don't re-debug these)

1. **New route files need a dev-server restart to get their Tailwind classes compiled.** Editing an existing file hot-reloads fine; adding a brand-new `page.tsx`/`layout.tsx` sometimes doesn't get scanned until the server restarts. Symptom: classes silently missing from the compiled CSS (`grep` the served `/_next/static/chunks/[root-of-the-server]*.css` for the class name to confirm) even though the page returns 200. Fix: kill and restart `npm run dev` before screenshotting a new route.
2. **`lsof` doesn't reliably work in this Windows Git Bash environment for killing the dev server.** Use this instead:
   ```bash
   PID=$(netstat -ano | grep ":3000" | grep LISTENING | head -1 | awk '{print $5}')
   taskkill //PID $PID //F
   sleep 2
   cd "C:\Users\123\Projects\webapp" && (npm run dev > /tmp/nextdev.log 2>&1 &) && timeout 40 bash -c 'until curl -sf http://localhost:3000/login >/dev/null 2>&1; do sleep 1; done' && echo READY
   ```
3. **Some plain numeric Tailwind utilities silently fail to compile** — confirmed missing: `gap-16`, `grid-cols-12`, `col-span-8`, `col-span-4`, `divide-y` (used with `divide-{color}`). Workaround used throughout: arbitrary-value gaps (`gap-[62px]`) instead of the numeric scale past ~10, and flexbox (`flex`, `flex-[2]`/`flex-[1]`, manual `border-t` per row) instead of CSS Grid utilities. Arbitrary bracket values (`gap-[50px]`, `w-[300px]`, etc.) have been reliable throughout — prefer them over the plain numeric scale if a class seems to not apply.
4. **A color token whose name contains the literal substring "border" breaks when combined with a Tailwind opacity modifier.** `border-light-border` alone works; `border-light-border/30` silently resolves to a default black border. Workaround: use the literal `rgba(...)` value in an arbitrary class instead, e.g. `border-[rgba(198,198,205,0.3)]` (this also happens to match Figma's own literal output in most cases, so no fidelity loss).
5. Playwright is installed as an ad-hoc devDependency (`npm install --no-save playwright`, plus a global browser install) purely for screenshot verification — it is **not** in `package.json`/`package-lock.json` and shouldn't be added there; reinstall the same way (`npm install --no-save playwright`, then `npx playwright install chromium`) in a fresh clone/session if screenshot tooling is needed again. Use the CLI directly rather than a custom script where possible: `npx playwright screenshot --viewport-size=1920,1080 --wait-for-timeout=800 "<url>" "<out.png>"`.
6. Figma's `get_design_context` sometimes silently omits a sub-tree of a large screen (observed: the shared `AppHeader` was missing from the Home dashboard's JSX dump even though it's visible in the screenshot). If a visible UI element is missing from the JSX, use `get_metadata` on the parent frame to find the node by name, then call `get_design_context` on that specific node ID directly.
7. Some Figma-exported icon assets are flattened to a single fill color matching whatever state they appeared in on the specific frame you pulled them from (e.g. sidebar icons come back navy if the nav item was active on that frame, white if inactive). Don't reuse one icon file across active/inactive states — either pull both states from Figma, or (what was done here) generate the other color variant locally via a `sed` fill/stroke swap on the SVG, since the shape is identical.

## Follow-up: React hydration mismatch on Sidebar's "Home" link — persona read from localStorage during initial render

The user pasted a real Next.js dev-overlay console error: a hydration mismatch on `Sidebar.tsx`'s Home `<Link>`, server-rendered `href="/home"` vs. client `href="/business/home"`.

**Root cause**: `persona` was read via a `useState` lazy initializer (`useState(readInitialPersona)`), and that initializer function runs *during* the hydration render itself. On the server, `typeof window === "undefined"` guards it to always return `"individual"`. On the client, the exact same function call (now running with `window` defined) can read `localStorage` and return `"business"` — so React computes a different `href` for the link than what's actually present in the server-rendered HTML, which React's hydration reconciliation flags as a mismatch. This is a different failure mode than the already-solved theme/dark-mode hydration issue elsewhere in this codebase: the theme toggle only ever varies a `data-theme` DOM attribute read by a CSS `@custom-variant`, which is invisible to React (React renders the identical className string on both server and client; only the browser's CSS engine's paint differs). `href` is a real React-tracked JSX prop, so it *is* diffed during hydration — the CSS-variant trick does not transfer to this case.

**First fix attempt (rejected by lint)**: default `useState` to `"individual"` and update it via a plain `useEffect(() => { ...; setPersona("business"); }, [])`. This is a legitimate, commonly-recommended pattern (matches React's own hydration-mismatch docs), but it tripped this project's `react-hooks/set-state-in-effect` ESLint rule, which flags synchronous `setState` calls inside an effect body as a cascading-render anti-pattern.

**Final fix**: replaced the `useState`/`useEffect` pair with `useSyncExternalStore` — React's purpose-built API for exactly this "read an external, client-only data source (localStorage) without causing a hydration mismatch" case, and it's lint-clean (no `setState`-in-effect involved at all):
```tsx
function subscribeToPersona(callback: () => void) {
  window.addEventListener("storage", callback);
  return () => window.removeEventListener("storage", callback);
}
function getPersonaSnapshot(): "individual" | "business" {
  try {
    return localStorage.getItem(PERSONA_STORAGE_KEY) === "business" ? "business" : "individual";
  } catch {
    return "individual";
  }
}
function getPersonaServerSnapshot(): "individual" | "business" {
  return "individual"; // server never has localStorage access
}
// ...
const persona = useSyncExternalStore(subscribeToPersona, getPersonaSnapshot, getPersonaServerSnapshot);
```
React guarantees the first client render uses `getPersonaServerSnapshot()` (matching the server exactly, so no mismatch), then swaps to the real `getPersonaSnapshot()` value in a safe, already-hydrated update. **This is now the preferred pattern for this codebase whenever client-only state (localStorage, `window`, etc.) needs to affect a React-tracked prop like `href`, `src`, or conditional JSX during the very first render** — prefer it over a `useState` + `useEffect` pair, which either risks a hydration mismatch (if read eagerly) or trips `react-hooks/set-state-in-effect` (if updated in an effect).

**Verified**: `npm run lint` and `npm run build` both clean. Playwright: loaded `/home` and `/business/home` fresh (no console errors), then specifically reproduced the original bug scenario — set `localStorage.vol-persona = "business"` and reloaded `/business/home` — confirmed zero console errors and the sidebar's Home link correctly resolves to `/business/home` with no hydration warning.

## Follow-up: app content stretched edge-to-edge on screens wider than Figma's 1920px canvas, shrinking the sidebar's proportion

The user reported the sidebar "not taking so much space as compared to Figma." Figma's canvas is a fixed 1920px design where the sidebar is 400/1920 ≈ 20.9% of the width — and at a 1920px (or narrower) viewport, this app already matched that ratio exactly. The bug only appears on screens **wider** than 1920px (e.g. a 2560px monitor): `Sidebar` and `AppHeader` are both `position: fixed` pinned to the true viewport edges, and `main` in `src/app/(app)/layout.tsx` had `lg:ml-[400px]` with no corresponding right-side constraint — so on a wider screen, `main` simply stretched to fill all the extra width while the sidebar stayed a fixed 400px, shrinking its visual proportion well below Figma's 20.9% (e.g. down to ~15.6% at 2560px, ~11.6% at 3440px ultrawide).

**Fixed** by centering the whole fixed-position composition once the viewport exceeds 1920px, using `max(fixed-value, calc((100vw - 1920px)/2 + fixed-value))`-style arbitrary values — this resolves to the exact original fixed-pixel value for any viewport ≤1920px (zero behavior change, verified unchanged at 1366px and 1920px), and beyond 1920px it shifts the sidebar's left edge, the header's left/right edges, and `main`'s left/right margins inward symmetrically, so the design keeps its correct Figma proportions and gutters grow evenly on both sides instead of content stretching unboundedly on one side only:
- `Sidebar.tsx`: `lg:left-[max(0px,calc((100vw-1920px)/2))]`
- `AppHeader.tsx`: `lg:left-[max(400px,calc((100vw-1920px)/2+400px))] lg:right-[max(0px,calc((100vw-1920px)/2))]`
- `(app)/layout.tsx`'s `main`: `lg:ml-[max(400px,calc((100vw-1920px)/2+400px))] lg:mr-[max(0px,calc((100vw-1920px)/2))]`

**Verified** via Playwright measuring the sidebar's actual rendered width/ratio at 1366px (400px, ratio 0.293 — unchanged), 1920px (400px, ratio 0.208 — unchanged, matches Figma), 2560px (sidebar now offset to start at x=320 instead of x=0, main/header symmetric right gutter of 320px, ratio restored toward Figma's proportion), and 3440px ultrawide (same symmetric-centering behavior). 0px horizontal overflow confirmed at 2560px. `npm run lint` and `npm run build` both clean.

## Follow-up: the ultra-wide sidebar fix above was incomplete — the sidebar was still disproportionately wide on ordinary laptop screens below 1920px

The user reported the sidebar still didn't match Figma's proportion after the previous fix. That fix only handled viewports **above** 1920px (correctly), but left the sidebar at a rigid fixed `400px` for every viewport from `lg` (1024px) up to 1920px — and most real laptop screens (1366×768, 1440×900, 1536×864 are among the most common desktop resolutions) fall well inside that range. At 1366px, a fixed 400px sidebar is 400/1366 ≈ 29.3% of the screen — **41% wider, proportionally, than Figma's 400/1920 ≈ 20.8%** — which is what the user was actually seeing, not the ultra-wide case.

**Fixed properly this time** by making the sidebar width itself scale with the viewport instead of being a fixed pixel value at any point below 1920px. Added two shared CSS custom properties in `globals.css`'s `:root` so the math lives in one place instead of being repeated (and potentially drifting) across three components:
```css
--app-sidebar-w: clamp(240px, 20.8333vw, 400px);
--app-wide-gutter: max(0px, calc((100vw - 1920px) / 2));
```
`--app-sidebar-w` scales proportionally with the viewport (20.8333vw = 400/1920 as a percentage) between a 240px usability floor (so nav labels/icons stay legible on narrower `lg` screens near 1024px) and Figma's exact 400px value, which it reaches and caps at exactly 1920px. `--app-wide-gutter` is the same centering offset as before, now expressed once instead of duplicated. `Sidebar.tsx`, `AppHeader.tsx`, and `(app)/layout.tsx`'s `main` now reference these vars instead of hardcoded `400px`/duplicated `calc()` expressions (e.g. `lg:w-[var(--app-sidebar-w)]`, `lg:ml-[calc(var(--app-sidebar-w)+var(--app-wide-gutter))]`).

**Verified** via Playwright measuring the sidebar's actual rendered width/ratio across seven viewports: 1024px → 240px (floored, ratio 0.234), 1280/1366/1440/1536/1920px → all land almost exactly on Figma's 0.208 ratio (e.g. 1366px → 284.6px sidebar, ratio 0.208 — down from the previous 400px/0.293), and 2560px → still correctly capped at 400px with the composition centered (from the prior follow-up, unaffected by this change). Screenshot at 1366px confirms nav items/icons/text still render cleanly at the smaller proportional width. `npm run lint` and `npm run build` both clean, 0px horizontal overflow confirmed at 1366px.

**Lesson for future viewport-fluid work in this codebase**: when Figma's design is a fixed reference canvas (1920px here) and a fixed-pixel measurement is ported directly to a `lg:` (or any single-breakpoint) Tailwind class, it only stays correct exactly at that one reference viewport — every other viewport inside that breakpoint's range silently drifts from Figma's actual proportion. Fixed sidebar/header/rail widths measured off Figma should generally be expressed as `clamp(floor, Xvw, Figma-px-value)` (where `X = Figma-px-value / 19.2` to convert to a vw percentage of the 1920px canvas), not `lg:w-[Figma-px-value]`, unless there's a specific reason the element should NOT scale between breakpoints.
